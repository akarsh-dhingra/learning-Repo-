Lesson 0005 · Build · ~60 min

Build an Excalidraw-style room server

Rooms, a snapshot for whoever joins late, two kinds of messages (durable strokes and throwaway cursors), and a real canvas client you can draw on with a friend.

You'll build: a multi-room whiteboard server with presence (who's here), live cursors and shared strokes, plus a browser client. Done when: 10/10 checks pass, and two browser windows draw on the same board.

1. The three ideas in every collaborative room

  1. Room = topic. Room id comes from the URL (?room=abc). Bun's ws.subscribe(room) plus publish do the fan-out. Validate the id before upgrading (HTTP 400), because it becomes part of keys and topics.
  2. Snapshot on join. A late joiner needs the current state, not the history of events. Send room.state as the very first message: { you, users, strokes }.
  3. Durable vs ephemeral. Strokes are durable: stored in the room, acked, and late joiners see them. Cursors are ephemeral: never stored, never acked, and losing one is harmless because the next replaces it. Keep this split: every later lesson (resume, backpressure, scaling) treats the two kinds differently.

2. Build it

Continue in ~/learning-websockets/build/rooms and reuse your protocol.ts from 0004. Reference: labs/0005-whiteboard-rooms/server.ts.

Step 1: room state in memory

type User = { id: string; name: string; color: string };
type Room = { users: Map<string, User>; strokes: Stroke[] };
const rooms = new Map<string, Room>();
const getRoom = (id: string) => rooms.get(id) ?? rooms.set(id, { users: new Map(), strokes: [] }).get(id)!;

// serialise ONCE per event, then fan out the same string to everyone
const event = (type: string, data: unknown) => JSON.stringify({ type, data });

Step 2: validate at the door

fetch(req, server) {
  const url = new URL(req.url);
  if (req.headers.get("upgrade")?.toLowerCase() === "websocket") {
    const room = url.searchParams.get("room") ?? "";
    if (!/^[a-z0-9-]{1,40}$/i.test(room)) return new Response("bad room", { status: 400 });
    const user = { id: crypto.randomUUID(), name: url.searchParams.get("name") || "anon", color: pickColor() };
    if (server.upgrade(req, { data: { user, room } })) return;
  }
  return serveStatic(url);   // your canvas page from ./public
}

Step 3: the join order matters

open(ws) {
  const room = getRoom(ws.data.room);
  send(ws, "room.state", { you: ws.data.user, users: [...room.users.values()], strokes: room.strokes }); // 1
  ws.publish(ws.data.room, event("user.joined", { user: ws.data.user }));                       // 2
  room.users.set(ws.data.user.id, ws.data.user);                                                // 3
  ws.subscribe(ws.data.room);                                                                   // 4
},
close(ws) {
  const room = getRoom(ws.data.room);
  room.users.delete(ws.data.user.id);
  server.publish(ws.data.room, event("user.left", { userId: ws.data.user.id }));
  if (room.users.size === 0) rooms.delete(ws.data.room);   // free memory (persist first in a real app)
}

Snapshot first, then subscribe: the joiner never sees an event before the state it applies to. On a single process this is safe because open is synchronous. (Lesson 0008 has to handle the multi-node case differently.)

Step 4: handlers

.on("cursor", z.object({ x: z.number(), y: z.number() }), ({ ws, data }) => {
  ws.publish(ws.data.room, event("cursor", { userId: ws.data.user.id, ...data }));   // no return → no ack
})
.on("stroke.add", z.object({ stroke: Stroke }), ({ ws, data }) => {
  const room = getRoom(ws.data.room);
  if (room.strokes.length >= 5000) throw new ClientError("limit", "room is full");   // bound everything
  room.strokes.push(data.stroke);
  ws.publish(ws.data.room, event("stroke.added", { userId: ws.data.user.id, stroke: data.stroke }));
  return { count: room.strokes.length };
})
.on("scene.clear", z.unknown(), ({ ws }) => {
  getRoom(ws.data.room).strokes = [];
  server.publish(ws.data.room, event("scene.cleared", { by: ws.data.user.id }));
});

Use the Stroke schema from the lab: id, hex color, width 1–20, and 1–2000 [x,y] points. Limits on everything a client sends are your memory-safety net.

Step 5: the browser client

Copy labs/0005-whiteboard-rooms/public/ into your build's public/. Read index.html: it shows the client-side patterns you'll reuse everywhere.

  • Optimistic UI: draw the stroke locally right away, send stroke.add, and roll back if the request rejects.
  • Client-side throttle: send cursors at most every 33 ms (~30/s), however fast the mouse moves.
  • Logical coordinates: a fixed 1200×800 canvas space, scaled by CSS, so every screen size agrees on where (300, 200) is.

5. System-design rep

60 seconds: “Two users drag the same rectangle at the same time. What does your server do, and what does each user see?”

A strong answer covers…
  • The server is the single point of order: it applies updates in the order it receives them, so last writer wins per property (x/y of that element). That's exactly Figma's approach.
  • Each client applies its own change optimistically, then converges when the server's broadcast arrives. A brief “snap” is acceptable.
  • For text editing inside an element you'd need more (CRDT/OT, e.g. Yjs), but shapes and positions are fine with LWW.
