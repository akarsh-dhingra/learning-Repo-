What a WebSocket really is

One HTTP request, one “101 Switching Protocols”, then the same TCP connection carries small binary frames in both directions until someone closes it.

Your win for this lesson: you run a WebSocket server written with zero libraries, read the handshake and the raw frame bytes it prints, and can decode any small frame by hand.

1. The problem: HTTP can't speak first

HTTP is request → response. The server answers, but only when the client asks. Every app in your mission needs the reverse: the server pushes something the moment it happens. That could be a cursor moving in Excalidraw, a trade on a CEX, a player walking past you in Gather Town, or a position update in a game.

TechniqueHow it worksFits when…
Short pollingClient asks “anything new?” every N secondsUpdates are rare and a delay of N seconds is fine
Long pollingServer holds the request open until it has news, then the client re-asksA fallback for networks that block WebSockets
Server-Sent EventsOne long HTTP response that streams events, server → client only[1]Live feeds where the client rarely talks back, e.g. a ticker
WebSocketOne persistent, full-duplex connection: either side sends at any time[2]Both sides talk often and latency matters: games, collaboration, trading

Why not just poll fast? Each poll is a full HTTP request with headers, often hundreds of bytes, to carry maybe 20 bytes of news. Polling also adds up to one poll interval of delay. A WebSocket frame adds only 2–14 bytes of overhead, and the server sends it the instant something happens.

2. The opening handshake

A WebSocket starts life as an ordinary HTTP/1.1 GET. That's deliberate: it uses ports 80/443 and passes through existing HTTP infrastructure[2]. The URL scheme is ws://, or wss:// for TLS (always use wss:// in production).

// client → server
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://example.com

// server → client
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

That exact pair is the example from RFC 6455 §1.3[2]. The accept value is computed like this:

Sec-WebSocket-Accept = base64( sha1( Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

The GUID is a fixed constant from the spec. This calculation is not authentication. It only proves the server really understood a WebSocket request and isn't some HTTP server that echoed headers back. After the 101, HTTP is over. The same TCP socket now carries frames.

Common belief“WebSockets are a separate protocol on their own port, so they skip HTTP entirely.”
What actually happensEvery WebSocket begins as an HTTP request. That's why your server's HTTP layer is where you check auth (cookies, a token in the query string) and the Origin header before you accept the upgrade. We'll build this in a later lesson.

3. Frames: the unit on the wire

After the handshake, everything is a frame. A message (what your code sees in onmessage) is one frame, or several fragments joined together. Here's the header from §5.2[2]:

Work it out once by hand. A server sends the text Hello:

  • Byte 0 = 0x81 = 1000 0001: FIN=1 (final fragment), RSV=000, opcode=1 (text).
  • Byte 1 = 0x05: MASK=0 (server frames aren't masked), length=5.
  • Then 48 65 6c 6c 6f, which is “Hello” in UTF-8. Total: 7 bytes.

Play with the decoder. Click the presets, then edit bytes and watch the fields change. The masked “Hello” is the RFC's own example (§5.7). The close frame came from the lab you'll run below.

4. Masking: why the client XORs everything

Every client→server frame carries a random 4-byte key, and its payload is XOR-ed with it: byte[i] ^ key[i % 4][2]. This isn't encryption, because the key is sent right next to the data. It exists to protect proxies. Without it, malicious script in a browser could send bytes that look like an HTTP request. A badly built caching proxy might believe them and cache a poisoned response for other users[2]. Random masking means script can't choose the exact bytes on the wire. A server MUST close the connection if it gets an unmasked client frame.

5. Control frames: ping, pong, close

  • Ping (0x9) / Pong (0xA): either side may ping, and the receiver MUST reply with a pong carrying the same data[2]. Servers use this as a heartbeat to find dead connections. TCP alone can take a very long time to notice that a laptop lid closed.
  • Close (0x8): carries an optional 2-byte status code. The other side replies with a close, then the TCP connection ends. That's the closing handshake.
CodeMeaning[2]Where you'll see it
1000Normal closureUser left the Excalidraw room
1001Going awayTab closed, or your server is shutting down for a deploy
1006Abnormal: no close frame received. Never sent, only reported locallyWi-Fi dropped, process crashed, proxy killed an idle connection
1008Policy violationBad auth token, rate limit exceeded
1009Message too bigClient sent more than your maxPayloadLength
1011Internal server errorUnhandled exception in your handler

Apps can also use their own codes in the 4000–4999 range, e.g. 4001 room full.

6. Lab: a WebSocket server with zero libraries

Open ~/learning-websockets/labs/0001-handshake-by-hand/server.mjs and read it top to bottom. It's about 70 lines: node:net for raw TCP, node:crypto for SHA-1, and everything from sections 2–5. Then run it:

cd ~/learning-websockets/labs/0001-handshake-by-hand
node server.mjs          # terminal 1
node client.mjs          # terminal 2: uses Node's built-in WebSocket client

What you should see in terminal 1 (abbreviated, from a real run on your machine):

── HTTP request from client ──
GET / HTTP/1.1
connection: upgrade
upgrade: websocket
sec-websocket-key: xwM7i0uXSzAPs/xuYNWAPg==
sec-websocket-version: 13
sec-websocket-extensions: permessage-deflate; client_max_window_bits
── frame bytes ── 81 95 51 f7 44 bc 39 92 …
FIN=true opcode=1 MASK=true len=21

── frame bytes ── 88 82 a6 f1 ad 20 a5 19 …

Notice 95 in byte 1: 1001 0101 means MASK=1 and length=21. Notice also that the client offered permessage-deflate compression and our server ignored it. That's allowed: the server simply doesn't list it in the response, so it isn't used. Now try it from a browser: open any page's dev console and run

const s = new WebSocket("ws://localhost:8081");
s.onmessage = (e) => console.log(e.data);
s.onopen = () => s.send("hi from chrome");

7. Recall first, then check

Answer out loud before opening each one. Answering from memory is what moves knowledge from “I've seen it” to “I know it”.

Walk through the handshake: which headers matter, and what status code? Client sends a GET with Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Key and Sec-WebSocket-Version: 13. Server replies 101 Switching Protocols with Sec-WebSocket-Accept = base64(sha1(key + GUID)). After that the TCP socket carries frames.
What's in the first two bytes of every frame? Byte 0: FIN, RSV1–3, opcode (4 bits). Byte 1: MASK bit plus a 7-bit length, where 126 or 127 means an extended length follows.
Who masks, and why? Only the client masks, on every frame, with a fresh random key. This stops browser script from writing chosen bytes that a broken proxy could mistake for HTTP and cache (cache poisoning).
Your user's phone drops off the subway Wi-Fi. What close code does the server see, and how does it find out? 1006 (abnormal, no close frame), and often only after a heartbeat ping goes unanswered or an idle timeout fires. TCP alone may not notice for minutes.

8. System-design rep

Set a 60-second timer and answer out loud: “Why does Excalidraw use WebSockets for live collaboration instead of polling an API?”

A strong answer covers…
  • Both directions are chatty: every user's cursor and edits go up, and everyone else's come down. That's full-duplex traffic.
  • Latency: a push arrives the instant it happens, while polling adds up to one poll interval.
  • Overhead: 2–14 bytes per frame versus full HTTP headers per poll. At 20–30 cursor updates/sec per user, that difference dominates.
  • The cost: a long-lived, stateful connection pinned to one server process. That's what makes scaling harder (lesson 0003).
