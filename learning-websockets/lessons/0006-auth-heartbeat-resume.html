Lesson 0006 · Build · ~75 min

Auth, heartbeats, reconnect & resume

Real connections drop: subway tunnels, laptop lids, deploys. A production socket layer is mostly about what happens around the messages.

You'll build: token auth and Origin checks at upgrade, token expiry, presence that survives multiple tabs, per-room sequence numbers with a replay log, and a client that reconnects with jittered backoff and resumes without losing a stroke. Done when: 10/10 checks pass, and the “Drop connection” button reconnects cleanly.

1. The connection lifecycle

2. Auth at the door

  • Browsers can't set headers on new WebSocket(). Your options are a cookie (sent automatically on the upgrade) or a token in the query string. We use a short-lived signed token: base64url(payload).base64url(HMAC-SHA256(secret, payloadPart)) with { sub, name, exp }. It's the same idea as a JWT. Your main API issues it, and the socket server only verifies it.
  • Check Origin. Browsers always send it on the upgrade. Without an allowlist, any website can open a socket to you with your user's cookies (cross-site WebSocket hijacking). Non-browser clients send no Origin, so you let them through and rely on the token.
  • Identity comes from the token, never from ?name=.
  • Tokens expire mid-connection. Set a timer for exp, close with your own code 4001, and have the client fetch a new token and reconnect at once.
if (origin && !ALLOWED_ORIGINS.includes(origin)) return new Response("bad origin", { status: 403 });
const auth = verifyToken(url.searchParams.get("token"));      // null if bad signature or expired
if (!auth) return new Response("invalid or expired token", { status: 401 });
// … in open():
ws.data.expiry = setTimeout(() => ws.close(4001, "token expired"), auth.exp * 1000 - Date.now());
// … in close(): clearTimeout(ws.data.expiry)

Copy labs/0006-auth-heartbeat-resume/auth.ts (30 lines: signToken, verifyToken with a constant-time compare). The checks sign their own tokens with the default secret, so keep the format.

3. Heartbeats: finding dead connections

A phone that loses signal sends nothing. No close frame, no FIN. Without heartbeats, the server keeps that socket (and its user in the presence list) for minutes.

  • Server side: Bun pings automatically and closes a socket after idleTimeout seconds of silence[1]. Set idleTimeout: 30. With ws on Node you write the ping/terminate loop yourself.
  • Client side: browser JS never sees protocol pings, so the client can't tell a dead link from a quiet room. Send an app-level ping request every 10 s. If there's no ack within 5 s, close and reconnect.

4. Presence per user, not per socket

Alice opens two tabs, then closes one. She must not “leave”. Keep Map<userId, { user, conns }>: announce user.joined on 0→1 and user.left on 1→0.

5. Sequence numbers and resume

This is the core of reliable delivery over an unreliable socket. Every durable event in a room gets the next number, and the room remembers the last 200:

function durable(roomId: string, type: string, data: unknown) {
  const room = getRoom(roomId);
  const msg = JSON.stringify({ type, seq: ++room.seq, data });
  room.log.push({ seq: room.seq, msg });
  if (room.log.length > 200) room.log.shift();
  return msg;
}

The client remembers the last seq it applied, and reconnects with ?lastSeq=41&epoch=…. In open:

const oldest = room.log[0]?.seq ?? room.seq + 1;
const canResume = lastSeq !== null && epoch === room.epoch && lastSeq <= room.seq && lastSeq >= oldest - 1;
if (canResume) send(ws, "room.resume", { you, users, events: logAfter(lastSeq), seq: room.seq, epoch: room.epoch });
else           send(ws, "room.state",  { you, users, strokes: room.strokes, seq: room.seq, epoch: room.epoch });
  • Epoch: a random id per room incarnation. If the server restarted and the room was rebuilt, seq 41 means something else now. A wrong epoch means a full snapshot.
  • Too old (the gap is bigger than the log): full snapshot. Resume is an optimisation, and the snapshot is always the safe fallback.
  • Keep empty rooms ~60 s so a quick reconnect can still resume.
  • Cursors and presence get no seq. Nobody needs to replay a cursor.

6. The reconnecting client

Read labs/0006-auth-heartbeat-resume/public/client.js. Then write your own and compare. The essentials:

export const backoff = (attempt) => Math.random() * Math.min(10_000, 500 * 2 ** attempt); // "full jitter"

ws.onclose = async (e) => {
  rejectAllPending();                              // in-flight requests fail fast
  if (stoppedByUser) return;
  if (e.code === 4001) { await refreshToken(); return connect(); }
  setTimeout(connect, backoff(attempt++));         // attempt resets to 0 on a successful open
};
// on any event with seq: if (seq <= lastSeq) drop it (duplicate), else apply and lastSeq = seq

Why jitter: when a node restarts, 50,000 clients disconnect in the same second. Without randomness they all retry at 0.5 s, then 1 s, then 2 s, in synchronized waves that knock the next node over. Full jitter spreads them evenly[2].

9. System-design rep

60 seconds: “You deploy a new version of your gateway. 40,000 users are connected to the old pods. Walk me through what happens to them, and how you keep it boring.”

A strong answer covers…
  • Old pods drain: fail health checks, stop taking new sockets, close existing ones with 1001 spread over a window (lesson 0012).
  • Clients reconnect with jittered backoff and land on new pods via the load balancer.
  • They resume with lastSeq + epoch. Room state lives outside the pod (Redis, lesson 0008), so the epoch survives the deploy and resume works, so nobody loses work.
  • Tokens are short-lived and refreshed on 4001. Watch connection-count and reconnect-rate dashboards during the rollout.
