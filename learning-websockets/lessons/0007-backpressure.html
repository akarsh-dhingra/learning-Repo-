Backpressure & slow consumers

One user on hotel Wi-Fi can't read as fast as you send. If you keep queueing, their buffer eats your server's memory. Decide what to drop, and when to cut them loose.

You'll build: cursor batching on a tick, skip-when-slow for droppable messages, a hard limit that terminates hopeless sockets (they resume via 0006), and a /stats endpoint. Then you'll watch a real stuck client get kicked. Done when: 3/3 checks pass.

1. Where the bytes go

ws.send() doesn't put bytes on the network. It puts them in a per-socket send buffer that drains as fast as the client reads. A fast server plus a slow reader means a buffer that grows without limit. You can see it with ws.getBufferedAmount() (Bun) or ws.bufferedAmount (ws / browser). Bun also tells you on every send: -1 means queued under backpressure, and 0 means dropped[1].

Message kindPolicy when the client is slowWhy
Ephemeral (cursors, positions, typing)Coalesce, then skip for that socketLatest value wins; a stale cursor has zero value
Durable (strokes, chat, orders)Never skip; past a hard limit, disconnectA gap corrupts state. Resume (0006) is the recovery path

2. Build it (continue in build/rooms)

Step 1: coalesce cursors and flush on a tick

Instead of publishing every cursor message, remember only the latest per user, and every 50 ms send one cursors batch per room. 30 moves/sec/user in becomes at most 20 batches/sec/room out, however many users are moving.

// handler: just remember
.on("cursor", z.object({ x: z.number(), y: z.number() }), ({ ws, data }) => {
  getRoom(ws.data.room).cursors.set(ws.data.user.id, { userId: ws.data.user.id, ...data });
})

// tick: one batch per room, serialised once, skipped for slow sockets
setInterval(() => {
  for (const room of rooms.values()) {
    if (room.cursors.size === 0) continue;
    const batch = JSON.stringify({ type: "cursors", data: [...room.cursors.values()] });
    room.cursors.clear();
    for (const ws of room.sockets) {
      if (ws.getBufferedAmount() > 64 * 1024) { stats.cursorDrops++; continue; }   // SOFT limit
      ws.send(batch);
    }
  }
}, 50);

Rooms now need a sockets: Set (add in open, delete in close) because you're sending per socket. The batch goes to everyone, sender included, so the client skips its own userId. That keeps “serialise once”.

Step 2: hard limit for durable events

function kickSlowConsumers(roomId: string) {
  for (const ws of getRoom(roomId).sockets) {
    if (ws.getBufferedAmount() > 1024 * 1024) {      // HARD limit: 1 MB behind
      stats.kicked++;
      ws.terminate();   // close() would queue a close frame BEHIND the backlog
    }
  }
}
// call it right after every durable publish (stroke.added, scene.cleared)

Set Bun's backpressureLimit above your hard limit (e.g. 4 MB) as a safety net. Past it, Bun silently drops messages for that socket, which is the one outcome you never want for durable events.

Step 3: /stats

const stats = { connections: 0, cursorBatches: 0, cursorDrops: 0, kicked: 0 };
if (url.pathname === "/stats") return Response.json(stats);

5. System-design rep

60 seconds: “On your CEX, a market-data client on a bad connection falls behind on the BTC order book. What do you do?”

A strong answer covers…
  • Order-book diffs are durable: skipping one silently corrupts the client's book. So never drop selectively. Past a buffer limit, disconnect.
  • The client reconnects and resyncs from a snapshot (lesson 0011). It's cheaper than buffering minutes of diffs.
  • Offer a lighter stream for weak clients: top-20 levels at 100 ms (a conflated snapshot) instead of every diff. Binance does exactly this with its partial-depth streams.
  • Monitor kicked and buffer sizes. A spike means a network problem or a too-chatty stream.
