The socket layer in production: the whole map

HTTP servers are interchangeable. WebSocket servers aren't. Every hard part of scaling real-time systems comes from that one fact.

Your win for this lesson: you can draw a production socket layer from memory, choose between the two scaling patterns for a given app (Excalidraw, Gather Town, CEX, game), and do the fan-out math that decides how many servers you need.

1. Why connections change everything

A REST request can land on any server, because the request carries everything it needs. A WebSocket is a long-lived, stateful connection: once user A's socket is open to gateway #2, only gateway #2 can write to it. Four consequences follow, and the rest of this course is about them:

  1. Cross-node broadcast. Alice is on node 1 and Bob is on node 2, in the same Excalidraw room. Node 1 can't write to Bob's socket. This is exactly what breaks when you run two copies of the assignment A2 rooms.ts.
  2. Load is measured in connections, not requests. A node with 50k idle sockets is busy even with zero traffic: each holds memory, a file descriptor and heartbeat timers.
  3. Deploys drop users. Restarting a node closes every socket on it (code 1001). Thousands of clients reconnect at once, which is called a reconnect storm.
  4. Messages can be lost in the gap. Anything sent while a client was reconnecting is gone unless you design for resume, using sequence numbers.

Slack's message path: the sender calls the API → the API hashes the channel ID to find its Channel Server → that server forwards to every Gateway subscribed to the channel → each Gateway writes to its local sockets. Delivery is worldwide in about 500 ms[1].

3. Two scaling patterns

Pattern A: any node + backplane

The load balancer puts each connection on any gateway. When a message arrives for room r, the gateway publishes it once to the backplane. Every gateway that has local members of r has subscribed to that channel. Each one receives the message and fans it out to its own sockets. Socket.IO calls this component an adapter, with Redis, Postgres and others as options[2].

  • Good for: chat, notifications, and CEX market data. One publisher (the matching engine) feeds many readers spread across many gateways.
  • Watch out: Redis Pub/Sub is at-most-once. “If the subscriber is unable to handle the message (for example, due to an error or a network disconnect) the message is forever lost”[3]. You need sequence numbers and a catch-up path, or Redis Streams. In Redis Cluster, use sharded Pub/Sub (SPUBLISH), so messages don't flood every node[3]. Your Redis course's hash-slot knowledge applies directly here.

Pattern B: room ownership (sharding by room)

Every room has exactly one owner process, picked by consistent hashing on the room ID. All of that room's traffic goes through its owner. Figma: “our servers currently spin up a separate process for each multiplayer document”, and “the server is the ultimate authority on what the document looks like”[4]. Discord does the same with a process per guild that fans out to session processes[5].

  • Good for: anything that needs one authoritative state and one order of events: Excalidraw/Figma documents, a Gather Town map's positions, a game world's simulation tick. One owner means a total order for free, so last-writer-wins becomes well defined.
  • Watch out: hot rooms. A 100k-member Discord server or a viral stream lands entirely on one owner. Owner failure needs a fast handover. Slack's replacements are ready in under 20 seconds[1].
Common belief“To scale WebSockets you need sticky sessions on the load balancer.”
More preciselyA WebSocket is one TCP connection, so it already stays on one server. Sticky sessions matter for long-polling fallbacks, where many separate HTTP requests must reach the same process[2]. What you might want instead is room affinity (Pattern B), which is a routing decision based on the room, not the client.

4. Fan-out math: the number that sizes everything

In a room where everyone sees everyone, each inbound message becomes N outbound messages. So outbound grows with N². Drag the sliders. Start with an Excalidraw room of 10 people sending 20 cursor updates per second. Then try a Gather Town space with 300 people moving at 10 updates/sec, first with everyone visible (100%), then with each person only seeing nearby avatars (5%).

At 300 users and 100% visibility, that's 900k msgs/s out of one room. That's half of your measured single-process Bun ceiling, for a single space. At 5% visibility, it drops to 45k. This trick is called interest management: only send each client what's near them. It's the single biggest lever for Gather Town and metaverse games, and it's why those apps shard by area, not just by room. Other levers, covered in later lessons:

  • Batch per tick: send one message every 50–100 ms with all changes, instead of one per change. Games call this the tick rate.
  • Deltas, not snapshots: send only what changed, plus a full snapshot when a client joins or falls behind. That's exactly how CEX order-book feeds work.
  • Serialise once: build the frame once per room message, not once per recipient. Bun's publish does this for you.
  • Drop, don't queue: for cursors and positions, only the latest value matters. A slow client should skip stale updates, not buffer them.

7. System-design rep

Take 5 minutes and sketch on paper: “Design the real-time layer for Excalidraw collaboration. Up to 50 users per room, 1M concurrent users total.” Then compare.

A strong answer covers…
  • Connections: wss:// through an L4/L7 LB to Bun gateways. Auth with a short-lived token checked in fetch before upgrade. If one gateway holds ~50k sockets, you need about 20+ gateways for 1M, plus headroom.
  • Routing: Pattern B. Hash the room ID to an owner, which orders the room's updates. Gateways forward to the owner and subscribe to its output. Or start with Pattern A and Redis while rooms are small.
  • Fan-out: 50 users × 20 cursor msgs/s × 50 recipients = 50k msgs/s per full room. So batch cursors every 50 ms, drop stale ones, and send scene edits as deltas.
  • Reliability: scene edits carry sequence numbers. On reconnect, the client sends its last seq and gets the missing deltas or a fresh snapshot. Cursors aren't persisted at all.
  • Ops: heartbeats, drain gateways before deploys (close 1001, client reconnects with jittered backoff), and alerts on connection count and send-queue size.
