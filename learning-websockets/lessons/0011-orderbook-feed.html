Lesson 0011 · Build · ~90 min

A CEX market-data gateway with gap-free order books

An exchange's socket layer has one writer (the matching engine) and a huge number of readers who must hold an exact copy of the book. Missing one diff isn't laggy, it's wrong.

You'll build: a market-data gateway (Pattern A, run two of them) with subscribe/unsubscribe streams, a REST snapshot endpoint, private per-user order streams, a token-bucket rate limit, and the client-side LocalBook that syncs from snapshot + diffs and detects gaps. Done when: 8/8 gateway checks and 5/5 LocalBook unit tests pass, and the UI stays “in sync” with simulated packet loss on.

2. The sync algorithm (the part interviewers ask about)

Straight from Binance's documentation, “How to manage a local order book correctly”[1]:

  1. Open the stream and buffer diffs. Note the U of the first one.
  2. Fetch the REST snapshot.
  3. If snapshot.lastUpdateId < first U − 1, the snapshot is too old: fetch again.
  4. Discard buffered diffs with u ≤ lastUpdateId. The snapshot already contains them.
  5. Set the book to the snapshot, then apply the remaining buffered diffs, then live ones.
  6. While live: if a diff's U > your lastUpdateId + 1, you missed something. Throw the book away and resync.

It's the same subscribe-then-snapshot ordering you used in 0008. That's not a coincidence: it's the pattern for “state + live updates” over any lossy pipe.

onDiff(diff) {
  if (!this.synced) return void this.buffer.push(diff);
  if (diff.u <= this.lastUpdateId) return;                  // old
  if (diff.U > this.lastUpdateId + 1) {                     // GAP: book is now wrong
    this.stats.gaps++; this.synced = false; this.buffer = [diff]; this.sync(); return;
  }
  this.apply(diff);
}
async sync() {
  for (;;) {
    const snap = await this.fetchSnapshot();
    if (this.buffer[0] && snap.lastUpdateId < this.buffer[0].U - 1) continue;   // too old, again
    this.bids = new Map(snap.bids); this.asks = new Map(snap.asks); this.lastUpdateId = snap.lastUpdateId;
    const pending = this.buffer.filter((d) => d.u > snap.lastUpdateId);
    this.buffer = []; this.synced = true;
    pending.forEach((d) => this.onDiff(d));
    return;
  }
}

3. Build it

New folder build/exchange. Copy engine.ts and auth.ts from labs/0011-orderbook-feed/ as-is, and write the gateway and LocalBook yourself.

Gateway spec (what the checks test)

  • GET /depth?symbol= → the snapshot JSON from Redis md:{sym}:book. POST /login → {token}.
  • Upgrade with an optional ?token=: none means anonymous (public data only), and a bad token means 401. Send welcome {node, authenticated, symbols}.
  • subscribe {streams} / unsubscribe {streams}: names like BTC-USD@depth, validated with Zod, at most 20 per connection, acked with the current list. Ref-counted Redis subscriptions per stream, exactly like 0008's attach/detach. Events go out as {type:"depth"|"trade", stream, data}.
  • Authenticated sockets are auto-subscribed to user:{sub}. order.place (validated) → publish to orders:in → ack {status:"submitted"}. The fill arrives later on the private stream. Anonymous → forbidden.
  • Rate limit: a token bucket per socket (burst 10, refill 5/s). Over the limit → error rate_limited and close 1008. Binance documents a 5 msg/s inbound limit for the same reason[1].
function allow(ws) {                         // token bucket: refill by elapsed time, spend one per message
  const now = performance.now();
  ws.data.tokens = Math.min(10, ws.data.tokens + ((now - ws.data.lastRefill) / 1000) * 5);
  ws.data.lastRefill = now;
  if (ws.data.tokens < 1) return false;
  ws.data.tokens -= 1; return true;
}

6. System-design rep

5 minutes: “Design market data for an exchange with 300 symbols and 2M connected clients. The BTC book changes 2,000 times a second.”

A strong answer covers…
  • One writer per symbol (the matching engine), publishing sequenced diffs to a durable log (Kafka, or an internal multicast bus) partitioned by symbol, not Redis Pub/Sub.
  • Fan-out tiers: engine → regional relays → thousands of stateless gateways. Each gateway subscribes once per symbol it has clients for, and serialises once per symbol, not per client.
  • Conflation for slow or retail clients: @depth20@100ms snapshots instead of every diff. Full diffs only for clients that keep up, with disconnect on lag.
  • Snapshots served from cache/CDN with lastUpdateId. Clients run the buffer → snapshot → apply → gap-resync algorithm.
  • Private streams by user id, authenticated with short-lived listen keys. Per-connection rate limits, a stream cap, and a 24 h max connection lifetime (Binance documents all three).
