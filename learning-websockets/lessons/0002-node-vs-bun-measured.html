Node vs Bun, measured on your machine

You asked which runtime pushes more messages per second. We measured it instead of guessing: on your M4, Bun delivered roughly 7–9× more messages than Node with ws.

Your win for this lesson: you can write the same chat-room server in both runtimes, rerun the benchmark yourself, and explain why one is faster and when that difference stops mattering.

1. What each runtime gives you

  • Node.js has a built-in WebSocket client (stable since v22.4) but no built-in server. You need a library[1]. The standard one is ws: a WebSocket implementation in JavaScript.
  • Bun has a server built into Bun.serve. It's built on uWebSockets, a C++ library, so framing, masking and broadcasting run in native code. It also has built-in pub/sub topics[2].
  • Not the same thing: Socket.IO is a protocol on top of WebSockets, with its own packet format, rooms, acks and a long-polling fallback. A plain new WebSocket() client can't talk to a Socket.IO server. This course uses plain WebSockets so you learn what Socket.IO hides.

2. The same server, twice

A chat room: every message from any client is broadcast to every connected client, including the sender. Both files are in labs/0002-node-vs-bun/.

// server-bun.ts
const server = Bun.serve({
  port: 8080,
  fetch(req, server) {
    if (server.upgrade(req)) return;      // sends the 101 for you
    return new Response("Expected a WebSocket upgrade", { status: 426 });
  },
  websocket: {                            // ONE handler object for all sockets
    open(ws)      { ws.subscribe("room"); },
    message(ws, m){ server.publish("room", m); },
  },
});
// server-node.mjs
import { WebSocketServer } from "ws";
const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (ws) => {           // listeners per socket
  ws.on("message", (data, isBinary) => {
    for (const client of wss.clients) {   // broadcast = a JS loop
      client.send(data, { binary: isBinary });
    }
  });
});

Look at the structure. Bun handles the upgrade inside a normal HTTP fetch handler, so you can check auth there before calling server.upgrade. That's the handshake from lesson 0001. Bun also has a native publish. With ws, you write the broadcast loop yourself.

4. Why Bun wins here

  1. Native hot path. Parsing frames, unmasking, and building outgoing frames all happen in C++ (uWebSockets). With ws, that work runs in JavaScript.
  2. Native fan-out. server.publish hands one message to the native layer, which delivers it to every subscriber. The Node server runs a JS loop of client.send(), so each call does its own JS work and crosses into the I/O layer separately. In a chat room, fan-out is the workload: 1 message in becomes N messages out.
  3. Less per-socket overhead. Bun shares one handler object across all connections instead of attaching listeners to each socket[2]. That matters when you hold 100k idle Gather Town connections.

5. Read the benchmark like an engineer

A benchmark answers exactly the question it asked. Before you quote “10×” in a design review, know its limits:

  • One process, one core. Both servers run JS on a single thread. Production runs one process per core, or many pods. So you'd compare 10 Bun processes against 10 Node processes, and the ratio holds but both scale up.
  • Empty handlers. Real handlers JSON.parse, validate, check permissions, and call Redis. That work costs the same in both runtimes and shrinks the gap. Measure your handler.
  • Same-machine load generator. The client competes with the server for CPU. Treat the numbers as relative, not absolute.
  • At scale, the bottleneck moves. Network egress, the pub/sub backplane between servers, and slow clients usually hit you before the runtime does (lesson 0003).
  • Need Node? uWebSockets.js brings the same C++ engine to Node.
Decision for this course: we build on Bun. It meets your “most messages per second” criterion, and its built-in topics map directly onto rooms, the core idea in Excalidraw, Gather Town and CEX channels. We'll keep socket logic behind small functions so the ideas transfer to Node + ws or uWebSockets.js.

6. The Bun API you'll use constantly

// Attach per-connection data at upgrade time (auth happens HERE)
fetch(req, server) {
  const url = new URL(req.url);
  const user = verifyToken(url.searchParams.get("token"));   // your function
  if (!user) return new Response("Unauthorized", { status: 401 });
  server.upgrade(req, { data: { userId: user.id, room: url.searchParams.get("room") } });
},
websocket: {
  data: {} as { userId: string; room: string },              // types ws.data
  open(ws)    { ws.subscribe(ws.data.room); },
  message(ws, msg) {
    ws.publish(ws.data.room, msg);      // everyone in the room EXCEPT the sender
    // server.publish(room, msg)        // everyone INCLUDING the sender
  },
  close(ws, code, reason) { /* closed sockets auto-unsubscribe */ },
  idleTimeout: 120,          // seconds; default 120. Bun pings for you
  maxPayloadLength: 16 * 1024 * 1024,  // default 16 MB; oversize → close 1009
}

One more thing to remember for later: ws.send() returns -1 when the message is queued under backpressure, 0 when it's dropped, and the number of bytes sent otherwise. The drain handler fires when the queue empties[2]. Slow consumers get a whole lesson later (0007).

8. System-design rep

60 seconds, out loud: “Your team wants to rewrite the CEX market-data gateway from Node + ws to Bun because ‘Bun is 7× faster’. What do you ask before agreeing?”

A strong answer covers…
  • Where's the bottleneck today? Profile it: is it CPU in framing and fan-out, JSON serialisation, the backplane, or network egress?
  • Benchmark our workload: real payload sizes, real fan-out ratio, real handler code. Look at p99 latency, not just throughput.
  • Cheaper options: serialise once per message rather than once per client, batch updates, or move to uWebSockets.js while staying on Node.
  • Risks: library compatibility in Bun, operational familiarity, and rollback plan.
