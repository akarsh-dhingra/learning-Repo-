Operating it: metrics, drains, load tests

You can't run what you can't see. Add the metrics that matter, make deploys boring, then load-test the 0008 cluster until it breaks, and find out why it broke.

You'll build: a Prometheus /metrics endpoint, graceful drain (failing health checks, refusing new sockets, closing existing ones spread over a window), and a WebSocket load generator. Done when: 2/2 checks pass, and you've reproduced the room-affinity result below on your machine.

Prometheus text format is just lines[1]:

# HELP ws_connections Open WebSocket connections
# TYPE ws_connections gauge
ws_connections{node="node-1"} 1667

Event-loop lag is the cheapest health signal there is. Schedule a 500 ms timer and record how late it fires.

2. Graceful drain: making deploys boring

  1. On SIGTERM (what Kubernetes and systemd send), set draining = true.
  2. /healthz returns 503, so the load balancer stops sending new connections.
  3. New upgrades get 503.
  4. Existing sockets are closed with 1001 “server restarting”, spread over DRAIN_MS. Dropping 50k at once makes 50k reconnects in the same second: a reconnect storm aimed at your remaining nodes.
  5. Clients reconnect with jittered backoff (0006), land on healthy nodes, and resume by seq with nothing lost, because state is in Redis (0008).
  6. Exit. Set the orchestrator's grace period longer than DRAIN_MS.
all.forEach((ws, i) => setTimeout(() => ws.close(1001, "server restarting"), (i / all.length) * DRAIN_MS));

4. Load test: the measurement that matters

loadtest.ts spreads N clients across the three nodes. Every client sends a cursor 10×/s, and one in ten draws a stroke every 2 s. It reports how long strokes take to reach other clients, plus per-node metrics. Real runs on your M4, 20 clients per room:

Debugging run B: where did 6.8 seconds go?

This is the actual investigation, step by step. Practise reading it, because this is the job:

  1. Server CPU? Loop lag stayed under 5 ms and the nodes sat at ~30–60% CPU. Not the nodes.
  2. Server send buffers? ws_max_buffered_bytes = 0 and no kicks. The nodes weren't waiting on clients.
  3. The load generator? Plausible at ~90% CPU, but splitting it into 2 and then 4 processes didn't help, and the four generators reported identical latencies. That points to a shared queue upstream of all of them.
  4. Redis? redis-cli -p 6390 client list showed each node's subscriber connection with omem of 2.5–11.6 MB: Pub/Sub output Redis was holding because the subscriber hadn't read it yet. Strokes were queued behind megabytes of cursor batches.
  5. Confirm: the same run with cursors off (CURSOR_HZ=0) gave p50 37 ms. The backplane was carrying traffic that didn't need to cross nodes.

Why: with round-robin, every room has users on all three nodes, so every node subscribes to every room and every cursor batch crosses the backplane to all of them. Fan-out traffic grows with nodes × rooms, the thing lesson 0003 warned about. Fix: route by room. AFFINITY=1 sends a room's clients to the node hash(room) picks, just like nginx's hash $arg_room consistent (in nginx.conf). Each node then only hears its own rooms: about 3× less backplane traffic, and p50 back to 43 ms.

Production danger you just metRedis's default client-output-buffer-limit pubsub 32mb 8mb 60 disconnects a subscriber whose buffer passes 32 MB, or stays above 8 MB for 60 s[2]. Run B was a few minutes from a node silently losing its whole backplane.
What to doGraph omem of your subscriber connections. Keep chatty ephemeral traffic off the backplane (affinity, or node-local fan-out), and make sure clients detect seq gaps and resume, because one day a subscriber will be dropped.
bun loadtest.ts 3000 150 15                 # run A
bun loadtest.ts 5000 250 15                 # run B   (clean between runs: redis-cli -p 6390 --scan --pattern 'room:*' | xargs redis-cli -p 6390 del)
AFFINITY=1 bun loadtest.ts 5000 250 15      # run C

Limits to know when load-testing from one laptop: each client socket uses an ephemeral port, and macOS gives you 49152–65535 (about 16k per destination). Your file-descriptor limit is in ulimit -n. Beyond ~10k sockets, test from several machines, with a dedicated tool such as k6, which has WebSocket support[3].

6. System-design rep

60 seconds: “What's on your socket-layer dashboard, and what wakes someone up at 3 am?”

A strong answer covers…
  • Dashboard: connections per node, connect/disconnect rate, messages in/out, delivery latency (synthetic probes), loop lag, memory per socket, kicks/drops, backplane subscriber buffer, Redis health.
  • Page on: a sudden connection drop across nodes, reconnect rate far above baseline (a storm), probe latency p99 over SLO, or loop lag above 100 ms sustained.
  • Ticket, don't page: a slow rise in kicks (often one ISP), memory growth (a leak), and imbalance between nodes.
