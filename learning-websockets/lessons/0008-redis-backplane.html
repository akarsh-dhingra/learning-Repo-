Many nodes, one room: the Redis backplane

Pattern A from lesson 0003, for real. Three Bun nodes, any user on any node, rooms that span them all, and resume that works even when you reconnect to a different node.

You'll build: your 0007 server, with room state, seq numbers, the resume log and presence moved into Redis, and Redis Pub/Sub as the backplane between nodes. Done when: 7/7 checks pass against two of your nodes, and a browser on :8081 sees strokes drawn on :8082.

2. The one rule that keeps it correct

Every room message goes through Redis, and a node only fans out what it receives from Redis, including its own events.

Why not fan out locally right away and publish to Redis for the other nodes? Because then node 1's users could see seq 6 (local, instant) before seq 5 (from node 2, via Redis). The client would treat 5 as a duplicate and drop it. That's silent data loss. Redis Pub/Sub delivers messages in the order they were published[1], so if seq assignment and publish happen as one atomic step, everyone sees the same order.

That atomic step is a Lua script. Redis runs a script without interleaving other commands:

local seq = redis.call('INCR', KEYS[1])                                    -- room:{id}:seq
local msg = '{"type":"' .. ARGV[1] .. '","seq":' .. seq .. ',"data":' .. ARGV[2] .. '}'
if ARGV[3] == 'add'   then redis.call('RPUSH', KEYS[3], ARGV[4]) end         -- the scene
if ARGV[3] == 'clear' then redis.call('DEL',   KEYS[3]) end
redis.call('RPUSH', KEYS[2], msg)                                          -- resume log…
redis.call('LTRIM', KEYS[2], -200, -1)                                     -- …capped at 200
redis.call('PUBLISH', KEYS[4], msg)                                        -- ch:room:{id}
return seq

Consequences you'll see in the checks: the sender now also receives its own stroke.added (with its seq), and its own user.joined. Clients dedupe strokes by id and ignore their own user id. Those are small prices for a single ordering.

3. Build it

Bun has a built-in Redis client with Pub/Sub (import { RedisClient } from "bun")[2]. A subscribed connection can't run other commands, so make a second one with await redis.duplicate(). Reference: labs/0008-redis-backplane/rooms.ts (all Redis code) and server.ts.

Step 1: subscribe per room, ref-counted

const subs = new Map<string, { count: number; ready: Promise<unknown>; listener: (m: string) => void }>();
export async function attach(room: string, deliver: (room: string, msg: string) => void) {
  let s = subs.get(room);
  if (!s) { const listener = (m: string) => deliver(room, m);
            subs.set(room, (s = { count: 0, listener, ready: sub.subscribe(`ch:room:${room}`, listener) })); }
  s.count++;
  await s.ready;                // the 2nd local joiner waits for the SAME subscribe
}
export async function detach(room: string) {
  const s = subs.get(room);
  if (!s || --s.count > 0) return;
  subs.delete(room);
  try { await s.ready; await sub.unsubscribe(`ch:room:${room}`, s.listener); }
  catch (err) { console.error(err); }   // cleanup must never crash the node
}

That try isn't decoration. While testing lesson 0011, a client that disconnected while its subscribe was still in flight made unsubscribe throw, and the unhandled rejection killed the whole gateway. Await ready first, and unsubscribe only your own listener.

Step 2: open() in the right order

async open(ws) {
  ws.subscribe(room); localRoom(room).sockets.add(ws);
  await rooms.attach(room, deliver);        // 1. start receiving live events…
  const snap = await rooms.snapshot(room);  // 2. …THEN read the snapshot
  send(ws, canResume ? "room.resume" : "room.state", …);
  if (await rooms.presenceJoin(room, user)) rooms.emitEphemeral(room, "user.joined", { user });
}

Subscribe before the snapshot, so nothing falls in the gap. Some events will then arrive before room.state. The client buffers anything with a seq until it has the snapshot, then replays only seq > snapshot.seq. That's the snapshot + buffered deltas pattern, which comes back in lesson 0011 as the official way to sync a CEX order book. See the synced/early logic in labs/0008-redis-backplane/public/client.js.

Step 3: deliver() is the only fan-out

function deliver(room: string, msg: string) {
  const lr = local.get(room); if (!lr) return;
  if (msg.startsWith('{"type":"cursors"')) { /* per-socket send with SOFT limit, as in 0007 */ return; }
  server.publish(room, msg);
  for (const ws of lr.sockets) if (ws.getBufferedAmount() > HARD_LIMIT) { stats.kicked++; ws.terminate(); }
}

Each node still batches its own users' cursors per tick and publishes the batch to Redis.

6. System-design rep

60 seconds: “Your backplane is Redis Pub/Sub. What breaks first as you grow, and what are your options?”

A strong answer covers…
  • Every node receives every message for every room it has a member in. With users spread randomly, that's nearly every room, so backplane traffic grows with nodes × rooms. Lesson 0012 measures this breaking.
  • Fixes: room affinity at the load balancer (rooms mostly live on one node), sharded Pub/Sub in Redis Cluster (SPUBLISH), or move to Pattern B (room owners, lesson 0010).
  • At-most-once delivery: gaps are covered by seq + resume. If you need durable fan-out, use Redis Streams, NATS JetStream or Kafka.
  • Redis is now a dependency for every message. Plan for Redis HA (replica + Sentinel, or managed), and decide what nodes do while Redis is down.
