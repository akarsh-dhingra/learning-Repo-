Design the message protocol

A WebSocket gives you a pipe, not an API. Before you build rooms, give every message one shape, one router, and one way to fail.

You'll build: a Bun server with a typed message router, Zod validation, request/response over the socket (acks and errors matched by id), and a chat lobby on top. Done when: 10/10 checks pass against your server.

1. Why you need a protocol

With HTTP you get routes, status codes and request/response for free. A WebSocket gives you message(ws, data) and nothing else. Every real app ends up building the same three pieces. Build them deliberately on day one:

  1. An envelope: every message is { type, id?, data? }. The type is your “route”.
  2. A router: a map from type to a handler, with a schema per type. Never trust client JSON.
  3. Request/response: if the client sends an id, it gets back exactly one ack or error with the same id. Without this, the client can't know whether a stroke or an order “landed”.
DirectionShapeExample
client → server{ type, id?, data? }{"type":"chat.send","id":"7","data":{"text":"hi"}}
server → client (reply){ type:"ack", id, data }{"type":"ack","id":"7","data":{"delivered":true}}
server → client (failure){ type:"error", id?, data:{ code, message } }{"type":"error","id":"7","data":{"code":"invalid",…}}
server → client (event){ type, data }{"type":"chat.message","data":{"from":"alice",…}}

Error codes are a small fixed set the client can switch on: bad_json, bad_envelope, unknown_type, invalid, forbidden, internal. Message text is for humans. Codes are for code. One rule matters a lot: a bad message gets an error, not a disconnect. Drop the connection only for abuse (lesson 0011's rate limit).

3. Build the router (protocol.ts)

The core idea in ~40 lines. Handlers return a value, and the router turns it into an ack. Handlers throw new ClientError(code, msg), and the router turns that into an error. Anything else that throws is a bug: log it and send internal. Never leak the stack trace to the client.

import { z } from "zod";
import type { ServerWebSocket } from "bun";

export const Envelope = z.object({
  type: z.string().min(1).max(64),
  id: z.string().max(64).optional(),
  data: z.unknown().optional(),
});
export class ClientError extends Error {
  constructor(public code: string, message: string) { super(message); }
}
export const send = (ws: ServerWebSocket<any>, type: string, data?: unknown, extra = {}) =>
  ws.send(JSON.stringify({ type, ...extra, data }));

export function createRouter<D>() {
  const routes = new Map<string, { schema: z.ZodType; handler: Function }>();
  return {
    on<S extends z.ZodType>(type: string, schema: S,
        handler: (ctx: { ws: ServerWebSocket<D>; data: z.infer<S>; id?: string }) => unknown) {
      routes.set(type, { schema, handler });
      return this;                                   // chainable
    },
    async handle(ws: ServerWebSocket<D>, raw: string | Buffer) {
      let id: string | undefined;
      try {
        let json; try { json = JSON.parse(String(raw)); } catch { throw new ClientError("bad_json", "not JSON"); }
        const env = Envelope.safeParse(json);
        if (!env.success) throw new ClientError("bad_envelope", "expected { type, id?, data? }");
        id = env.data.id;
        const route = routes.get(env.data.type);
        if (!route) throw new ClientError("unknown_type", `unknown type ${env.data.type}`);
        const parsed = route.schema.safeParse(env.data.data);
        if (!parsed.success) throw new ClientError("invalid", z.prettifyError(parsed.error));
        const result = await route.handler({ ws, data: parsed.data, id });
        if (id) send(ws, "ack", result ?? null, { id });   // no id → fire-and-forget, no reply
      } catch (err) {
        if (err instanceof ClientError) send(ws, "error", { code: err.code, message: err.message }, { id });
        else { console.error(err); send(ws, "error", { code: "internal", message: "internal error" }, { id }); }
      }
    },
  };
}

4. Build the server (server.ts)

Spec for this lesson's server (the checks test exactly this):

  • Upgrade at /?name=alice. Store { name } in ws.data, subscribe everyone to topic "lobby", and send welcome {name} on open.
  • ping → ack { time: Date.now() }. echo → ack with the same data.
  • chat.send {text}: trimmed, 1–500 chars. Broadcast chat.message {from, text, at} to everyone, sender included, and ack {delivered:true}. Text starting with /admin → forbidden, not broadcast.
const router = createRouter<{ name: string }>()
  .on("ping", z.unknown(), () => ({ time: Date.now() }))
  .on("echo", z.unknown(), ({ data }) => data)
  .on("chat.send", z.object({ text: z.string().trim().min(1).max(500) }), ({ ws, data }) => {
    if (data.text.startsWith("/admin")) throw new ClientError("forbidden", "you are not an admin");
    server.publish("lobby", JSON.stringify({ type: "chat.message",
      data: { from: ws.data.name, text: data.text, at: Date.now() } }));
    return { delivered: true };
  });

const server = Bun.serve({
  port: 8080,
  fetch(req, server) {
    const name = new URL(req.url).searchParams.get("name")?.slice(0, 32) || "anon";
    if (server.upgrade(req, { data: { name } })) return;
    return new Response("WebSocket only", { status: 426 });
  },
  websocket: {
    data: {} as { name: string },
    open(ws) { ws.subscribe("lobby"); send(ws, "welcome", { name: ws.data.name }); },
    message(ws, raw) { router.handle(ws, raw); },
  },
});

The checks connect as real clients and test every rule above: garbage JSON keeps the socket alive, unknown types echo the id, the 501-char limit, sender-included broadcast, and /admin never broadcast. Red → read the failure message → fix → rerun. That loop is the lesson.

TemptingName events after UI actions ("buttonClicked"), send whole objects “just in case”, and add id to every message.
BetterName by domain, noun.verb: chat.send, stroke.add, order.place. Send the minimum. Use an id only when the client needs to know the outcome. High-frequency fire-and-forget traffic (cursors, positions) has no id and no ack.

7. System-design rep

60 seconds, out loud: “Your mobile app and web app share one WebSocket API. Next month you'll change chat.message's fields. How do you avoid breaking old app versions?”

A strong answer covers…
  • Make only additive changes to existing types: add fields, never rename or remove them. Old clients ignore unknown fields.
  • For a breaking change, use a new type (chat.message.v2) or a protocol version negotiated at connect time (?v=2, or the Sec-WebSocket-Protocol header), and serve both until old versions die out.
  • Use Zod schemas as the single source of truth. Share the types with the client (a monorepo package) so drift becomes a compile error.
