Rate limiting: from a counter to a sliding window

The video builds a counter with a TTL. You'll make it atomic, see where fixed windows leak, and switch to a sorted set when that leak matters.

Your win: a running Express API that returns 429 with Retry-After after 10 requests per user, using a race-free Lua script, plus a sliding-window version you can explain step by step.

1. The video's design: fixed window

Give each user a counter key with a TTL equal to the window (for example 1 hour). On each request, INCR it. If the result is above N, reject. When the TTL expires the key disappears, and the next request starts again at 1. This works well because INCR is atomic and TTLs clean up for free[1].

The race the INCR docs warn about

If you write it as two calls (INCR, then EXPIRE if the result was 1), a client that crashes between the two leaves a counter with no TTL. That user stays blocked forever once they pass N. The official fix is to do both in one Lua script, which Redis runs atomically[1]:

local n = redis.call("INCR", KEYS[1])
if n == 1 then
  redis.call("PEXPIRE", KEYS[1], ARGV[1])   -- only the first hit starts the window
end
return { n, redis.call("PTTL", KEYS[1]) }
Why set the TTL only when n == 1, and not on every request? If you reset the TTL on every hit, a client that keeps calling pushes the window forward forever. Its counter never expires, so it stays blocked indefinitely even at a modest rate.

The leak: bursts at the boundary

limit = 10 per minute, fixed windows [00:00–01:00) [01:00–02:00) 00:59.5 10 requests → all allowed (window 1 count = 10) 01:00.1 10 requests → all allowed (window 2 count = 10) → 20 requests in 0.6 seconds, double the intended rate

2. Sliding window log (sorted set)

Store one sorted-set member per request, with the timestamp as its score. On each request, run one atomic script:

  1. ZREMRANGEBYSCORE key -inf now-window: drop requests that have aged out.
  2. ZCARD key: count what's left.
  3. If the count is below the limit, ZADD key now <unique-id> and refresh the key's TTL. Allow.
  4. Otherwise reject. Retry-after = (oldest score + window) − now.

No boundary burst: the window always looks back exactly 60 s from now. The cost is memory, one entry per request in the window. That's fine at 10 per minute, but expensive at 10,000 per second per user.

Fixed windowSliding log
Memory per userOne integerOne entry per request in the window
Boundary burstUp to 2× the limitNone
Redis typesString + INCRSorted set

Two more names to know for interviews: sliding window counter (blend the current and previous fixed-window counts) and token bucket (tokens refill at a steady rate, which allows short bursts). Both can also be built as one Lua script.
