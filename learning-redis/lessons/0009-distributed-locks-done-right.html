Distributed locks, part 1: a lock that's actually correct

The video's BookMyShow lock gets the idea right and the mechanics wrong. This lesson takes it apart and rebuilds it the way the Redis docs specify.

Your win: you can write SET key token NX PX ttl and the compare-and-delete release from memory, and explain the specific failure each part prevents. That covers parts 1, 2 and 5 of Assignment A1.

1. What a lock must guarantee

The Redis docs list three properties as the minimum for a useful distributed lock[1]:

  1. Safety (mutual exclusion): at any moment, at most one client holds the lock.
  2. Deadlock-free: even if the holder crashes or gets cut off, the lock eventually becomes available again.
  3. Fault tolerant: clients can still lock and unlock while some Redis nodes are down. That's Lesson 0010.

Keep these in mind. Every design choice below exists to protect one of them.

2. The video's lock, and why it breaks

The video uses a counter: each process INCRs the lock key. Whoever gets 1 holds the lock, anyone who gets more than 1 is blocked, a TTL frees it if the holder dies, and the holder deletes the key when done. Run it against the three properties:

FlawWhat goes wrongProperty broken
Losers INCR tooEvery blocked attempt bumps the counter. Nothing ever decrements it, so the value means nothing beyond “not 1”.Code smell, not a direct break
INCR and TTL are separateIf the winner crashes after INCR but before setting the TTL, the key never expires. Nobody gets the seat again.Deadlock-free
Release is a plain DELA slow holder whose TTL already expired deletes the next holder's lock, and now a third client gets in too.Safety
No owner identityThe key doesn't record who holds it, so nobody can check “is this still mine?” before acting.Safety

3. The correct single-instance lock

Acquire: one atomic command

SET lock:seat:A1 <random-token> NX PX 30000

NX sets the key only if it doesn't exist, and PX attaches an expiry in milliseconds, in the same atomic step. The value must be unique across all clients and all lock requests. The docs suggest 20 random bytes[1]. Reply OK means you hold it, and nil means someone else does.

Release: delete only if it's still yours

if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

Because the whole script runs atomically, nobody can sneak in between the GET and the DEL. On Redis 8.4+ the single command DELEX key IFEQ token does the same thing[1]. Your container runs 7.4, so you'll use the script.

Watch the bug the token prevents

t=0 A: SET lock tokA NX PX 100 → OK (A holds it) t=50 A: starts a slow DB call… t=100 lock expires (TTL) t=110 B: SET lock tokB NX PX 100 → OK (B holds it) t=130 A: finishes and releases plain DEL → deletes B's lock ✗ (C can now get in alongside B) compare-and-del → GET = tokB ≠ tokA → returns 0 ✓ (B keeps it)

Retry and always release

  • Retry with a random delay. If many clients retry on the same schedule, they keep colliding. The docs recommend a random delay before retrying[1].
  • Release in finally. An exception inside your critical section must not leave the lock held until the TTL runs out.
  • Choosing the TTL. It should be comfortably longer than the work normally takes, but short enough that a crash only blocks the resource briefly. The TTL is the window in which you're guaranteed exclusivity[1]. If your work can run longer, you need extend (a compare-and-PEXPIRE script) or fencing (Lesson 0010).

4. In Node, the shape you'll build in A1

const lock = await acquire(redis, "seat:A1", 2000);   // SET … NX PX via a script
if (!lock) return { ok: false, reason: "busy" };
try {
  const holder = await db.getSeat("A1");              // read…
  if (holder) return { ok: false, reason: "taken" };
  await db.writeSeat("A1", userId, lock.fence);       // …then write, inside the lock
  return { ok: true };
} finally {
  await release(redis, lock);                          // compare-and-delete
}
