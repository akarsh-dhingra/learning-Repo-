Hot keys: when one key melts one node

A celebrity's profile, a flash-sale product, the IPL score. Sharding can't help when the whole crowd wants the same key.

Your win: you can name three fixes from the video plus one it skips, say what each costs, and pick the right one for a scenario. That's exactly how this comes up in interviews.

1. The problem

A hot key gets far more traffic than any other key. Every request for it hashes to the same slot, so they all hit the same primary (Lesson 0005). Adding nodes spreads other keys but does nothing for this one. The video points out the same problem exists in any distributed cache: Memcached and DynamoDB have it too.

2. Three fixes from the video

FixHowCosts
1. Read from replicasAdd replicas to that shard and send reads to them. In a cluster, a connection sends READONLY to read from a replica[1].Replica reads can be slightly stale (async replication, Lesson 0004). Only helps reads.
2. Split the keyStore N copies: user:42:profile:1 … :N. Readers pick a random suffix, so the copies hash to different slots and nodes.Every write must update all N copies. Copies can briefly disagree. More memory.
3. Local in-app cacheA small LRU map inside each app server, checked before Redis, with a very short TTL (the video says 50–200 ms).Each server can be stale for up to that TTL. Memory per server. Thousands of requests never leave the process.

Fix 3 is something the Redis docs cover directly. Client-side caching keeps popular values in application memory, and Redis 6+ can tell your client when a cached key changes (“tracking” and invalidation messages), so you don't have to rely only on a short TTL[2]. The docs also give a rule for what to cache this way: keys requested often that change at a reasonable rate, not a counter that's incremented constantly[2].

3. One the video skips: the stampede

A hot key's TTL expires. In the same millisecond, 5,000 requests miss and all of them query Postgres. This is a cache stampede (also called the thundering herd), and the database is the one that falls over.

  • Single-flight: on a miss, only the request that wins SET rebuild:product:42 1 NX PX 5000 queries the DB. The others wait briefly and re-read the cache. That's a tiny lock, a preview of Lesson 0009.
  • Jittered TTLs: EX 600 + random(0..60), so keys cached together don't all expire together.
  • Refresh ahead: rebuild in the background when the TTL is nearly up, so readers never see a miss.

4. Finding hot keys

redis-cli --hotkeys samples keys by access frequency, but it only works when maxmemory-policy is an LFU policy[3], because it relies on LFU's frequency counters. Try it on your container:

docker exec redis-stack redis-cli CONFIG SET maxmemory-policy allkeys-lfu
docker exec redis-stack redis-cli -r 2000 GET product:42 > /dev/null   # make one key hot (it must exist: run the 0006 lab first)
docker exec redis-stack redis-cli --hotkeys
docker exec redis-stack redis-cli CONFIG SET maxmemory-policy noeviction  # restore
The video calls fix 2“cache breaking … using key sharding” and shows reads spreading across copies.
Don't forgetThe write side. With N copies, an update must touch all N (or delete all N). A reader can briefly see the old value on some copies. Mention this cost before the interviewer does.

5. Scenario drill

Live cricket score: 2M reads/sec on one key, updated every few seconds, slight lag is fine.

Flash-sale stock:iphone is decremented 50k times/sec. Which fix from the table helps most?

Every hour on the hour, DB CPU spikes to 100% for two seconds. Likely cause?

Recall: why doesn't adding nodes help a hot key? (One sentence.) One key hashes to one slot owned by one primary, so new nodes take other slots but never that one.
