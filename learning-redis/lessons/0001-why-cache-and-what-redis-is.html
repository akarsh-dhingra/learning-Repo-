Why cache, and why Redis is fast

The opening minutes of the video in one idea: stop asking the database the same question twice.

Your win for this lesson: you can draw the cache-aside flow from memory, predict whether a request is a hit or a miss, and give a 60-second interview answer on why Redis is fast and what it gives up.

1. The problem

The video opens with a profile screen. Every time a user opens the app, the server reads their name, username and email from the database. At a few users this is fine. At a million users, the database answers the same unchanging question over and over, gets overloaded, and every query slows down.

The key observation: profile data is read far more often than it changes. That is the signature of data worth caching.

2. The fix: cache-aside

Put a fast in-memory store beside the server and let the application manage it. This pattern is called cache-aside (also “lazy loading”)[1].

  1. A request arrives. The server asks Redis for the key first (e.g. user:42).
  2. Hit: Redis has it, so return it straight away. The database is never touched.
  3. Miss: Redis does not have it, so the server queries the database.
  4. The server writes the result into Redis with a TTL (time to live), then responds. The next request for that key is a hit.

Notice who does the work: your app reads the DB and fills Redis. Redis never talks to your database. That is why it's called cache-aside: the cache sits to one side of your app and your app decides what goes in it. A bonus from the same source: if Redis goes down, the app can fall back to the database and keep working, only slower[1].

3. What Redis is

Redis is an in-memory key-value data store. Every piece of data has a string key, and the value can be a plain string or a real data structure (list, hash, set, sorted set…). Redis's own FAQ puts it as “an in-memory but persistent on disk database”: very fast reads and writes, but your data set can't be bigger than your RAM[2].

The video lists four jobs you'll meet later in this course: cache (most common), message broker (Pub/Sub), distributed lock, and stream processing.

4. Why it's fast, and what it gives up

ReasonWhat it means
Data lives in RAMNo disk seeks on the read path. Disk is only used for saving copies (persistence).
Commands run one at a timeNo locks or race conditions between commands, and no time lost switching between threads.
Simple in-memory structuresData structures in RAM are much simpler to work with than the same structures on disk[2].

The price is durability. RAM is lost when the machine dies. Redis can save copies to disk in two ways[3]:

  • RDB: snapshots of everything, taken every few minutes. If Redis crashes, you lose whatever changed since the last snapshot.
  • AOF (append-only file): a log of every write. By default it's flushed to disk every second, so a crash loses about one second of writes.
  • Or no persistence at all, which is common for a pure cache. If you lose the cache, you just refill it from the DB.
The video saysRedis is “up to 100× faster than MySQL or MongoDB” and “single-threaded”, and only AOF is mentioned for persistence.
The docs sayTreat “100×” as a rough figure, not a benchmark. The FAQ quotes about 1M requests/sec with pipelining and says Redis usually runs out of memory or network before CPU. Command execution is single-threaded, but Redis already uses background threads for some work. RDB snapshots are on by default and AOF is opt-in[2][3].

If you need Redis behaviour with stronger durability, the video points to managed options with disk-backed storage (it names AWS MemoryDB), which are a bit slower.

5. Practice: recall first, then check

Close your eyes or cover the page, answer out loud, then open each one. Answering from memory before you look is what makes it stick.

Say the four cache-aside steps in order. Check Redis → hit: return → miss: query DB → write to Redis with a TTL, then return.
Name three reasons Redis is fast. RAM storage; commands run one at a time, so no locks and no time lost switching threads; simple in-memory data structures.
What's the trade-off, in one sentence? Redis trades durability for speed: data in RAM can be lost, and even with AOF set to flush every second you can lose about a second of writes.

6. Interview rep

Set a 60-second timer and answer out loud: “Our profile endpoint is slow under load. What would you do?” Then compare.

A strong answer covers…
  • Spot the pattern: many reads, few changes, so it's a good thing to cache.
  • Cache-aside with Redis: check the cache, on a miss read the DB, write with a TTL, return.
  • Why Redis: data lives in RAM so reads are very fast, and it takes repeated read load off the DB.
  • Trade-offs: stale data for up to the TTL (fix by deleting the key when the profile updates); RAM is limited; durability doesn't matter much for a cache, since the DB still has the real data.
