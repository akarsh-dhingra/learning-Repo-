Stale reads, replicas, and failover

Two short video sections that interviewers dig into: “is the cache consistent?” and “what happens when the Redis box dies?”

Your win: you run a primary and a replica on your laptop, see a replica refuse a write, and can explain why a replica is not a backup of the last second of writes.

1. Caches are eventually consistent

The video's Instagram example: a post's like count is cached with a 10-minute TTL. New likes go to the database, but readers see the cached number until the key expires. The data catches up eventually rather than immediately.

You have two levers:

  • Shorter TTL: less staleness, more DB load.
  • Invalidate on write: after updating the DB, DEL the cache key so the next read refills it. You'll build this in Lesson 0006. Delete rather than overwrite with the new value: if two writers race, overwriting can leave the older value in the cache, while deleting just forces a fresh read.

How replication really works

  • Replication is asynchronous by default. The primary replies “OK” to your client before the replicas have the write[1].
  • Replicas are read-only by default and reject writes[1].
  • WAIT n timeout blocks until n replicas confirm the write. It makes data loss much less likely, but the docs say it does not make Redis strongly consistent: acknowledged writes can still be lost during a failover[1].
  • Plain replication doesn't promote replicas by itself. Automatic failover comes from Redis Sentinel or Redis Cluster[1].
The video saysIf the main node fails, “we will serve the data from the replica”, and replicas hold the same data as the main.
The docs addA replica holds almost the same data: anything the primary acknowledged but hadn't sent yet is lost on failover. And something (Sentinel or Cluster) has to do the promoting. Also: a primary with persistence off that auto-restarts comes back empty, and its replicas then copy the empty dataset and wipe their own data[1].

3. Hands-on: a primary and a replica (6 min)

# put the existing redis-stack container on a network with a new replica
docker network create redis-net
docker network connect redis-net redis-stack
docker run -d --name redis-replica --network redis-net -p 6380:6379 \
  -e REDIS_ARGS="--replicaof redis-stack 6379" redis/redis-stack-server:latest

docker exec redis-stack   redis-cli SET greeting hello
docker exec redis-replica redis-cli GET greeting          # "hello"
docker exec redis-replica redis-cli SET greeting bye      # READONLY error
docker exec redis-replica redis-cli INFO replication | grep -E "^role|link_status"
docker exec redis-stack   redis-cli WAIT 1 1000           # 1 replica acknowledged

I tested these exact commands. Use the redis-stack-server image for the replica: the plain redis image crashes because it can't load Redis Stack's module data.

Now simulate a lag: docker pause redis-replica, write a new value on the primary, read the replica (it hangs while paused), then docker unpause redis-replica and watch it catch up. Clean up with docker rm -f redis-replica.
