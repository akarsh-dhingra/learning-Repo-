Caching Postgres for real, and measuring honestly

1. Recap in one diagram's worth of words

3. What the numbers really say

Here's what I got on your machine:

cold  p50=0.53ms  p95=1.41ms  p99=2.41ms  sources={"db":200}
warm  p50=0.14ms  p95=0.18ms  p99=0.28ms  sources={"cache":200}

The cache is about 4× faster, and its tail latency is far tighter. But a primary-key lookup on a local Postgres already takes only half a millisecond. The video's 117 ms vs 25 ms was mostly first-request costs (new connections, cold buffers), not the steady-state gap.

The interview-grade takeaway: caching pays most when the source is expensive (joins, aggregations, a remote or overloaded DB, a third-party API) or when load on the DB is the problem, not when a single indexed lookup is slow. Always measure p95/p99, not just one request.

4. The write path: invalidate

The lab adds PUT /products/:id/price. It updates Postgres first, then runs DEL product:<id>. The next GET misses and refills with the new price:

curl -s localhost:3000/products/42                      # source: db, price 48.05
curl -s localhost:3000/products/42                      # source: cache
curl -s -X PUT -H 'content-type: application/json' \
  -d '{"price":9.99}' localhost:3000/products/42/price   # invalidated: product:42
curl -s localhost:3000/products/42                      # source: db, price 9.99
Why update the DB first and delete the cache second, rather than the other way round? If you delete first, another request can miss, read the old row (your UPDATE hasn't committed yet), and put the stale value back into the cache. It then stays stale for the full TTL. Updating first shrinks that window a lot, though it doesn't eliminate it, which is why you still keep a TTL as a safety net.

5. When memory runs out: eviction

By default maxmemory is 0 (no limit on 64-bit). When you set a limit, the maxmemory-policy decides what gets dropped[1]:

PolicyEvictsUse when
noevictionNothing: writes error outRedis holds data you can't lose
allkeys-lruLeast recently used, any keyGood default for a cache (a small set of keys gets most reads)
allkeys-lfuLeast frequently usedPopularity is steady over time
volatile-*Only keys with a TTLCache and persistent data share one instance (the docs suggest two instances instead)

LRU in Redis is approximated by sampling a few keys, which saves memory and is close to true LRU in practice[1]. Track your hit rate as keyspace_hits / (keyspace_hits + keyspace_misses) from INFO stats.
