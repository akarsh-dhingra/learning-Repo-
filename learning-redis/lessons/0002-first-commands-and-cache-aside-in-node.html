Run Redis, then cache a slow API

The video's first demo, rebuilt so you can run it: a few commands by hand, then cache-aside in about 40 lines of Node.

Your win for this lesson: Redis running on your laptop, a correct prediction for what TTL returns in four tricky cases, and a Node endpoint that goes from about 100 ms to a few ms on the second call.

1. Start Redis

Start Docker Desktop first (the daemon wasn't running when I checked your machine). Then run the same image the video uses. It includes Redis on 6379 and the RedisInsight web UI on 8001:

docker run -d --name redis-stack -p 6379:6379 -p 8001:8001 redis/redis-stack:latest
docker ps                     # should list redis-stack
open http://localhost:8001    # RedisInsight: keys on the left, values on the right

Open a CLI inside the container[1]:

docker exec -it redis-stack redis-cli

2. Six commands, then four predictions

CommandDoes
SET name aniketStore a string under a key. Overwrites any existing value.
GET nameRead it back. Returns (nil) if the key doesn't exist.
SET name aniket EX 30Store it and give it a 30-second TTL in one atomic command.
TTL nameSeconds left. -1 = no expiry set. -2 = key doesn't exist[2].
INCR countTreat the value as an integer and add 1, atomically.
SET k v NXOnly set it if the key doesn't exist yet (the video's NX demo).

Key names follow the video's convention entity:id (user:42, post:10). RedisInsight's tree view groups keys by the colon.

Predict first, then run it in redis-cli

Pick an answer before typing the commands. Being wrong here is useful: it shows you exactly which mental model to fix.

SET name aniket → TTL name

TTL ghost (a key you never set)

SET name aniket EX 100 → SET name yannick → TTL name

SET count 4 EX 100 → INCR count → TTL count

The video doesSets the value and its expiry as separate steps (the TTL is set from the RedisInsight UI) and adds NX later on.
PreferSET key value EX n as one command. If your app crashes between a SET and a separate EXPIRE, the key never expires. And as you just saw, any later plain SET removes the TTL anyway[2].

3. Cache-aside in Node

The video's demo calls JSONPlaceholder (a free fake API) and caches each post under post:<id>. Your copy is ready to run at ~/learning-redis/labs/0002-cache-aside/ (dependencies are already installed). Here's the core of it, using the official node-redis client[3]:

const key = `post:${req.params.id}`;

// 1. Check the cache first
const cached = await redis.get(key);
if (cached) return res.json({ source: "redis", data: JSON.parse(cached) });

// 2. Miss: go to the slow source of truth
const data = await (await fetch(`https://jsonplaceholder.typicode.com/posts/${req.params.id}`)).json();

// 3. Fill the cache with a TTL, then respond
await redis.set(key, JSON.stringify(data), { EX: 600 });
res.json({ source: "external-api", data });

Two details: Redis stores strings, so objects go in with JSON.stringify and come out with JSON.parse. And node-redis takes options as an object, so { EX: 600 } is the same as EX 600 in the CLI[4].

Run it

cd ~/learning-redis/labs/0002-cache-aside
npm start
# in another terminal
curl -s localhost:3000/posts/10 | head -c 80; echo   # source: external-api
curl -s localhost:3000/posts/10 | head -c 80; echo   # source: redis — compare "ms"

In the video the first call took a few hundred ms and the cached one about 10 ms. Write down your two numbers. Then, in redis-cli:

TTL post:10     # counting down from 600
DEL post:10     # next curl is a miss again

4. Bring it to your project

Pick one read-heavy GET endpoint in your own code (a hotel or listing detail page in ~/hotelBookingPlatform is a good fit) and wrap it in the same three steps. Note the latency before and after, because “p50 went from X to Y ms” is a great line in an interview. Ask me if you'd like a hand with it.

Interview rep: “What could go wrong with the cache you just added?”
  • Stale reads for up to the TTL. Fix: DEL the key when the data is written (invalidation).
  • Forgotten TTL or a plain SET overwriting one, so keys live forever.
  • Bad keys: a key that leaves out part of the query (ID, locale, user) serves the wrong data.
  • Redis down: cache-aside can fall back to the DB, but make sure Redis errors don't crash the request.

Primary source

The official EXPIRE / TTL docs. Read “Details” and “How Redis expires keys” (about 6 min). It explains exactly why the SET-vs-INCR prediction behaves the way it does.
