Distributed locks, part 2: leases, fencing tokens, and the Redlock debate

A correct lock from Lesson 0009 can still let two clients act at once. This lesson shows exactly when, and the one technique that makes it safe anyway.

Your win: you can explain the paused-client failure on a whiteboard, add fencing tokens that make it harmless, describe Redlock and the strongest criticism of it, and decide whether Redis should be the lock at all, which is the senior-level part of the answer.

1. A Redis lock is a lease

Because of the TTL, you don't hold the lock forever. You hold it until the lease ends. The docs say mutual exclusion is guaranteed only while the holder finishes its work within that validity time, minus a little for clock drift[1]. Two things can break that assumption without any bug in your code.

Failure 1: the paused client

t=0 A acquires lock (TTL 10s), fence = 33 t=1 A's process freezes: GC pause, VM migration, swapped to disk… t=10 lease expires; Redis deletes the key t=11 B acquires lock, fence = 34; B books seat A1 for Bob t=15 A wakes up. From A's point of view no time passed. It still "holds" the lock. t=15 A books seat A1 for Alice ✗ Two holders acted on the same seat.

Martin Kleppmann's analysis turns on this case. A can't detect it because the pause happened between checking the lock and doing the write, and the storage has no way of knowing A's lease ran out[2]. Checking “do I still hold it?” right before writing doesn't help, because the pause can happen just after the check.

Failure 2: failover loses the lock

1. A acquires the lock on the primary. 2. The primary crashes before replicating the key (replication is async). 3. A replica is promoted. It has never seen A's lock. 4. B acquires the same lock. ✗ Safety violated.

The Redis docs list this exact race as the reason a primary plus replica setup isn't enough for a safe lock[1].

2. The fix that works for both: fencing tokens

Every successful acquire returns a number that always increases (33, 34, 35…). The client sends that number with every write, and the storage rejects any write whose token is lower than one it has already accepted[2].

t=11 B writes seat A1 with fence 34 → storage records lastFence = 34 ✓ t=15 A writes seat A1 with fence 33 → 33 < 34 → REJECTED ✓

Two key points:

  • The check lives in the storage, not in Redis. The storage is the one place every write passes through, so it's the only place a stale writer can be stopped. In Postgres it's one conditional update: 
    UPDATE seats
   SET holder = $1, fence = $2
 WHERE id = $3 AND fence < $2;     -- 0 rows updated ⇒ you were fenced off
  • Issue the fence atomically with the lock. In Redis, INCR fence:{seat:A1} runs in the same Lua script as SET … NX PX. Otherwise a client can stall between the two steps and end up with a newer fence than the client that acquired after it. The A1 test “do NOT advance on a failed acquire” checks this.

The Redis docs now say it directly: if you care about correctness, implement fencing tokens, and don't assume you still hold a lock just because your process is alive. They also note that Redis TTLs follow the wall clock, so a jump in the system clock can expire a lock early[1].

3. Redlock: the fault-tolerant variant

To get rid of the single point of failure without replication, the Redis docs describe Redlock across N independent primaries (they use N = 5)[1]:

  1. Record the start time.
  2. Try SET key token NX PX ttl on all N nodes in parallel, with a short per-node timeout.
  3. You hold the lock only if you got a majority (≥ 3 of 5) and the total time spent is less than the TTL.
  4. Your remaining validity = TTL − time spent (minus an allowance for clock drift).
  5. If you failed, release on all nodes, retry after a random delay.

The docs also cover what happens when a node crashes and restarts: with the default fsync of every second, a restarted node can forget a lock it granted. The fixes are fsync always or keeping a crashed node out for longer than the max TTL (“delayed restart”)[1].

The debate in four lines

Kleppmann (2016)Locks serve either efficiency (avoid duplicate work) or correctness (avoid corruption). Redlock is heavy for the first and unsafe for the second: it depends on timing assumptions about delays, pauses and clocks, and its random tokens can't be ordered for fencing. For correctness, use a consensus system (ZooKeeper, etcd) with fencing[2].
antirez (reply)If your storage can already reject stale tokens, it's doing the protection itself and the lock is only an optimisation. The random token can be used for check-and-set. And Redlock re-checks elapsed time after acquiring, so delays during acquisition don't break it; they just shorten the usable window[3].

You don't need to “win” this debate in an interview. You need to show you know it exists and land on a sound conclusion: for correctness, fencing at the storage is what you rely on. The lock reduces contention.

4. Decide: should Redis be the lock?

SituationReasonable choice
Avoid duplicate work (two cron workers sending the same report, rebuilding the same cache entry)Single-instance Redis lock. An occasional double run is acceptable (efficiency lock).
The data lives in one Postgres and the rule is “one row wins”Let the DB enforce it: a UNIQUE constraint, SELECT … FOR UPDATE, or a conditional UPDATE … WHERE. The video makes the same point: use a Redis lock only when your main DB can't guarantee consistency.
Seat hold for 10 minutes during payment across servicesRedis lease (fast, auto-expiring) plus a fenced or conditional write when confirming the booking in the DB.
Correctness-critical, and storage can't check tokens (external API, payments)Consensus-backed lock (etcd/ZooKeeper) plus idempotency keys on the external call. Redis alone isn't enough.

6. Interview rep (out loud, 90 seconds)

“Design the seat-hold for a movie booking app. Two users tap the same seat at the same time.”

A strong answer covers…
  1. Hold: SET hold:{show:101:A1} <token> NX PX 600000 plus a fence via INCR in the same script. The first to tap wins and the others see “unavailable”.
  2. Abandon: the TTL expires and the seat frees itself, so no cleanup job is needed.
  3. Confirm: after payment, UPDATE seats … WHERE id = $3 AND fence < $2 (or a UNIQUE(show_id, seat) on bookings). The DB is the final judge.
  4. Release with compare-and-delete. Never a plain DEL.
  5. Failure modes: GC pauses or failover can create two holders, and the fenced write makes that harmless. Redlock or etcd only if the lock alone must be correct.
  6. Idempotency key on the payment call so a retry doesn't charge twice.
