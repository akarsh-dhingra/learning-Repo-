Redis Cluster: slots, redirects, failover

The most interview-heavy section of the video. One formula decides where every key lives, and almost everything else follows from it.

Your win: you compute which node owns a key, design keys so related data stays together, and watch a real 6-node cluster send MOVED and survive a dead primary.

1. Why shard at all

Replicas (Lesson 0004) scale reads, but every write still goes to one primary, and the whole dataset must fit in that primary's RAM. Sharding spreads keys across several primaries, so writes and memory scale out. Each primary can still have its own replicas.

2. The one formula

The keyspace is split into exactly 16 384 hash slots. Every key maps to one slot[1]:

HASH_SLOT = CRC16(key) mod 16384

Each primary owns ranges of slots. The video's image of slots as buckets is right: nodes hold slots and slots hold keys. With 3 primaries the default split is A: 0–5460, B: 5461–10922, C: 10923–16383. That's exactly what my test cluster printed.

Hash tags: keeping keys together on purpose

If a key contains {…} with something inside, only that part is hashed. So {user:42}.cart and {user:42}.profile land in the same slot[1]. This matters because multi-key commands (MSET, transactions, Lua scripts touching two keys) only work if every key is in one slot. Otherwise you get a CROSSSLOT error. The A1 lock uses lock:{seat:A1} and fence:{seat:A1} for exactly this reason.

3. How a request finds its node

  1. On connect, the client fetches the slot → node map (CLUSTER SHARDS) and caches it.
  2. For each command it hashes the key, looks up the node, and connects to it directly, with no proxy in between.
  3. If the node doesn't own that slot, it replies -MOVED 3999 127.0.0.1:6381. The client retries there and should refresh its map, since several slots have probably moved[1].
  4. While a slot is being migrated, a node may reply -ASK instead. That means: try the other node for this one query (prefixed with ASKING), but don't update your map yet[1].
The video saysIf a request reaches the wrong node, nodes use gossip to “redirect it to the correct node”, and the slot count is “approximately” 16384.
The spec saysNodes don't forward your request. They reply with MOVED and the client resends it. Gossip (over the cluster bus, port + 10000) is how nodes learn about each other's health and slot ownership, not how requests get routed. The count is exactly 16384[1].

4. Failure and failover

  • A node that doesn't answer a ping for longer than NODE_TIMEOUT is marked PFAIL (possibly failed). Once a majority of primaries agree, it becomes FAIL[1].
  • That primary's replicas then call an election, the other primaries vote, and the winner takes over its slots. The spec says failovers usually take 1–2 seconds after detection[1].
  • Replication is still asynchronous, so a write acknowledged just before the crash can be lost. During a network split, the side with fewer primaries stops accepting writes once NODE_TIMEOUT has passed[1].

5. Hands-on: a real cluster (8 min)

sh ~/learning-redis/labs/0005-cluster/start-cluster.sh
docker exec -it redis-cluster redis-cli -p 7000       # WITHOUT -c first
127.0.0.1:7000> SET foo bar          # → MOVED 12182 127.0.0.1:7002
127.0.0.1:7000> CLUSTER KEYSLOT foo  # 12182: matches the calculator
127.0.0.1:7000> exit
docker exec -it redis-cluster redis-cli -c -p 7000    # -c follows redirects
127.0.0.1:7000> SET foo bar          # redirected to 7002, OK
127.0.0.1:7002> MSET a 1 b 2         # CROSSSLOT error
127.0.0.1:7002> MSET {u:1}.a 1 {u:1}.b 2   # OK: same slot
127.0.0.1:7002> CLUSTER NODES

Kill a primary and watch the failover:

docker exec redis-cluster redis-cli -p 7002 SHUTDOWN NOSAVE
sleep 8
docker exec redis-cluster redis-cli -p 7000 CLUSTER NODES   # 7002 master,fail; a replica is now master
docker exec redis-cluster redis-cli -c -p 7000 GET foo      # still "bar"
docker rm -f redis-cluster                                  # when done

When I ran this, replica 7005 took over slots 10923–16383 and GET foo still returned bar.
