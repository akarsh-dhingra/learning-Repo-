Pick the right structure

Redis is a “data structure server”. The design skill is choosing the structure whose built-in operations already do your job.

Your win: given a product feature, you name the Redis type and the two commands you'd use, without looking. Then you model a mini BookMyShow in redis-cli.

1. One key, many shapes

Keys are always strings. The value can be any of these types, each with its own commands[1]. The video demos strings, lists, hashes and geo. Sets and sorted sets matter just as much for interviews.

2. The details that come up in interviews

Strings

Up to 512 MB per value. INCR/INCRBY are atomic, so a thousand clients can increment the same counter without losing updates. SET k v NX means “only if absent”. Lesson 0009 builds a lock from it.

Lists

Pushing and popping at the same end gives you a stack (LIFO); opposite ends give you a queue (FIFO). The video demos the stack case: two LPUSHes, then LPOP returns the last one pushed. LTRIM key 0 99 after each push keeps a capped “latest 100” list.

Hash vs JSON string

In Lesson 0002 you cached posts as JSON strings. A hash stores the same object field by field. Use a hash when you read or update individual fields (HINCRBY product:7 stock -1). Use a JSON string when you always read or write the whole object at once, as a cache usually does.

Sets and sorted sets

SADD returns 1 if the member was new and 0 if it was already there. That makes it a one-command duplicate check. Sorted sets keep members ordered by score, so “top 10” is just ZRANGE key 0 9 REV WITHSCORES.

Geo

GEOADD key longitude latitude member. Longitude comes first, a common mistake. GEOSEARCH key FROMLONLAT lon lat BYRADIUS 5 km WITHDIST finds members within the radius, which is the video's bike-rental station example.

Pub/Sub vs Streams

Pub/Sub is at-most-once: if a subscriber is disconnected or fails while handling a message, that message is lost for good. For stronger guarantees the docs point to Streams, which keep messages and support at-least-once delivery[2]. In an interview: use Pub/Sub for live notifications where missing one is fine, and Streams for jobs or events you can't afford to lose.

The video saysRedis covers time series and Bloom filters alongside the core types, and that Redis can replace Kafka/SNS/SQS.
More preciselyTime series and Bloom filters ship with Redis Stack / Redis 8, not classic open-source Redis 7. “Replace Kafka” only holds for small, simple workloads (the video's own caveat). Pub/Sub alone can't replace a queue because it doesn't keep messages[2].

3. Drill: pick the structure

A live game leaderboard: add points to a player and show the top 10.

Record which users liked a post, with no duplicates, and check “did I like it?” fast.

Show a user's 20 most recent activity events.

A product record where checkout decrements just the stock field.

Count a user's requests in the last 60 seconds (sliding window).

Order events must reach the email worker even if it was down for a minute.

Recall: which end do LPUSH and RPOP use, and what structure do they make together? LPUSH adds at the head and RPOP removes from the tail. Opposite ends give you a FIFO queue.
Recall: what's the difference between Pub/Sub and Streams, in one line? Pub/Sub delivers at most once and keeps nothing. Streams keep messages and support at-least-once delivery with consumer groups.

Assignment 0003: model a mini BookMyShow in redis-cli

≈12 min · docker exec -it redis-stack redis-cli · watch it in RedisInsight (localhost:8001, tree view)

  1. Show record (hash): create show:101 with fields movie, screen, starts_at, seats_left = 120. Decrement seats_left by 2 with one command.
  2. Booked seats (set): add A1 A2 to show:101:booked. Try adding A2 again. Which return value tells you it's already booked?
  3. Trending (sorted set): every booking runs ZINCRBY trending 1 <movie>. Book 3× dune, 1× oppenheimer, 2× barbie, then print the top 2 with scores.
  4. Activity feed (list): push 5 events onto user:42:feed and keep only the latest 3. Prove it with LRANGE.
  5. Theatres nearby (geo): add three theatres to theatres using real coordinates in your city. Find the ones within 5 km of where you are, with distances.

Then paste your command history to me in the terminal for review. Bonus question: in step 2, why is the set's duplicate check not enough to stop two people booking A3 at the same instant if your app first runs SISMEMBER and only then SADD? (You'll fix this properly in A1.)
