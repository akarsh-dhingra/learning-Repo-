Replication & Cluster

Replication

  • Asynchronous by default: the primary acknowledges before replicas have the write.
  • Replicas are read-only (READONLY error on writes).
  • WAIT n ms reduces the chance of losing a write but does not make Redis strongly consistent.
  • Automatic failover needs Sentinel or Cluster. Plain replication doesn't promote anything.
  • Never auto-restart a primary that has persistence off: it comes back empty and its replicas copy the empty dataset.

Cluster in eight lines

  1. 16384 slots. slot = CRC16(key) mod 16384.
  2. Each primary owns slot ranges. With 3 primaries: 0–5460, 5461–10922, 10923–16383.
  3. Hash tag: only the text inside the first non-empty {…} is hashed. {user:42}.cart and {user:42}.orders share a slot.
  4. Multi-key commands and scripts need every key in one slot, otherwise you get CROSSSLOT.
  5. The client caches the slot → node map (CLUSTER SHARDS) and talks to nodes directly, with no proxy.
  6. MOVED slot host:port: the slot has moved for good. Retry there and refresh the map.
  7. ASK slot host:port: the slot is mid-migration. Retry once there with ASKING and keep the map unchanged.
  8. Failure: no reply for NODE_TIMEOUT → PFAIL; once a majority of primaries agree → FAIL; then a replica election promotes one replica. Async replication still means a small write-loss window.

Commands

CLUSTER KEYSLOT <key>        CLUSTER NODES        CLUSTER SHARDS
CLUSTER INFO                 CLUSTER COUNTKEYSINSLOT <slot>
redis-cli -c -p 7000         # -c follows MOVED/ASK
