Rate limiting

Fixed window (INCR + TTL on first hit)

local n = redis.call("INCR", KEYS[1])
if n == 1 then redis.call("PEXPIRE", KEYS[1], ARGV[1]) end
return { n, redis.call("PTTL", KEYS[1]) }

Leak: up to 2× the limit across a window boundary.

Sliding window log (sorted set)

ZREMRANGEBYSCORE k -inf (now - window)
if ZCARD k < limit: ZADD k now <unique>; PEXPIRE k window; allow
else: reject, retry after (oldest score + window - now)

No boundary burst. Memory = one entry per request in the window.

if redis.call("set", KEYS[1], ARGV[1], "NX", "PX", ARGV[2]) then
  return redis.call("incr", KEYS[2])
end
return 0

-- release (KEYS: lock · ARGV: token) → 1 or 0
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end
return 0

-- extend (KEYS: lock · ARGV: token, ttlMs) → 1 or 0
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("pexpire", KEYS[1], ARGV[2]) end
return 0

Fenced write in Postgres

UPDATE seats SET holder = $1, fence = $2 WHERE id = $3 AND fence < $2;   -- 0 rows ⇒ fenced off

Redlock (N = 5)

Lock all nodes in parallel with short timeouts. You hold it if you got ≥ 3 nodes and the elapsed time is under the TTL. Validity = TTL − elapsed − drift. If you failed, unlock everywhere. Safety depends on timing assumptions, so use fencing for correctness.

Which lock?

  • Efficiency (duplicate work is just wasteful): single Redis instance.
  • Correctness, and the data is in one DB: DB constraint / FOR UPDATE / conditional update.
  • Correctness across services: lease (Redis or etcd) plus a fenced write.
